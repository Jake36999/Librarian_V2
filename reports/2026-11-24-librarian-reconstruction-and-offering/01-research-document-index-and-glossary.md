### 1.2 Document Status Taxonomy Used in Index

- `IMPLEMENTED_VERIFIED`: Behavior/contract matches code and verified runtime logs/tests.
- `IMPLEMENTED_PARTIAL`: Part of the specification is implemented in code, while named obligations remain partial or open.
- `ACCEPTED_NORMATIVE`: Normative rule, directive, or methodological standard accepted by the Owner as governing.
- `ACCEPTED_UNIMPLEMENTED`: Owner-accepted target design or settled milestone/release item not yet implemented.
- `PROPOSED_UNACCEPTED`: Proposal, draft review, or generated diagram without Owner acceptance.
- `UNIMPLEMENTED_UNDROPPED`: Specified in V1 or earlier V2 design, absent/unwired in current code, **with NO decision to reject or drop it**.
- `DECIDED_AGAINST`: Explicitly rejected, retired (`graphify`), withdrawn (`isolated-incomplete-examples`), or superseded by an accepted successor.
- `UNRESOLVED_CONFLICTING`: Active conflict across records or open Owner design choice requiring explicit resolution.

## 4. Project Glossary and Semantic-Evolution Register

All project-specific terms below preserve exact project spelling from `DOC-POL-04`, `DOC-POL-02`, `DOC-V1D-05`, and `DOC-V1D-44`. Special attention is paid to **homonym collisions** (notably three distinct meanings of *Tier* and the Medallion `bronze/silver/gold` vs Trust `bronze/silver/gold` collision) and terms whose operational meaning shifted between V1 and V2.

### 4.1 Data (DIK Layer 1) / Bronze (Medallion Layer 1)
- **Aliases:** `Raw Data`, `Bronze Layer`, `Semantics (Owner informal frame)`
- **Canonical Definition:** The immutable captured artifact and mechanical structural facts derived before interpretation (`EvidenceStore` `.evidence/<kind>/<sha256>.json`, `.librarian/quarantine/`, `.librarian/intake_queue.json`, `folder_intake` inventory facts, `.librarian/derived/dik/` component/chapter structures). May assert only that a component/byte sequence existed at a source/commit/date.
- **Evolution / Superseded Usage:** V1 stored `.Data/surveys/*.json` & `source_components.sqlite`; V2 unified evidence into content-addressed `.evidence/` + structured `dik.py` JSON sidecars + explicit `quarantine/`. Must NOT be confused with Trust Tier `bronze`.
- **Authoritative Sources:** `DOC-V1D-05`, `DOC-V1D-06`, `DOC-V1D-39`, `DOC-V1D-44`

### 4.2 Information (DIK Layer 2) / Silver (Medallion Layer 2)
- **Aliases:** `Curated Information`, `Silver Layer`, `Semiotics (Owner informal frame)`
- **Canonical Definition:** Cleaned, conformed, **unframed (project-neutral)** descriptions emerging from relating Data points (`**Not read:**` where inferred in V1; in V2: hidden `.librarian/conversions/<evidence-id>.md` page-anchored text, `.librarian/staging/` airlock items, promoted `Sources/<kind>/<name>.md`, `Concepts/`, and rebuildable `.librarian/index.sqlite` / `Indexes/` / `.librarian/derived/paper-graph/`).
- **Evolution / Superseded Usage:** V1 placed Resource notes here manually with `## Evidence` & `**Not read:**` guards; V2 added the hidden page-anchored `.librarian/conversions/` layer for third-party content governance and formal Staging CAS/lease airlock. Must NOT be confused with Trust Tier `silver`.
- **Authoritative Sources:** `DOC-V1D-05`, `DOC-V1D-07`, `DOC-V1D-08`, `DOC-POL-06`, `DOC-POL-07`

### 4.3 Knowledge (DIK Layer 3) / Gold (Medallion Layer 3)
- **Aliases:** `Framed Knowledge`, `Gold Layer`, `Pragmatics (Owner informal frame)`
- **Canonical Definition:** Information interpreted and tested **against a specific project need, perspective, or real execution** (`Transferable Capability`, `Session`, `Brief`, `Candidate`, verified `Offerings/` gated by `EVIDENCE_QUOTE_VERIFIED`, and real-use `Applications/`). Knowledge cannot be asserted solely from a README; it requires either a new framing perspective over held Data/Information or real Application evidence.
- **Evolution / Superseded Usage:** V1 separated `09-Applications/` and `branch offerings/`; V2 formalized prospective knowledge as `Offerings/` (created in `synthesise` with exact substring quote verification) and realised knowledge as `Applications/`. Must NOT be confused with Trust Tier `gold`.
- **Authoritative Sources:** `DOC-V1D-05`, `DOC-V1D-06`, `DOC-V1D-08`, `DOC-V1D-46`

### 4.4 Medallion Architecture (Agnostic Definition)
- **Aliases:** `Bronze / Silver / Gold Storage Refinement`
- **Canonical Definition:** Grading material by level of refinement so that every derived stage is reproducible from the immutable stage before it, and errors are corrected by **replaying** rather than patching in place.
- **Evolution / Superseded Usage:** Adopted from lakehouse terminology (`Victor-Kipruto-Rop`, `DOC-V1D-39`) and generalized in `Use Contexts And Agnostic Description` (`DOC-V1D-08`) to govern V1/V2 vault storage + rebuildable indexes (`MARKDOWN_IS_TRUTH` + `EvidenceStore`).
- **Authoritative Sources:** `DOC-V1D-08`, `DOC-V1D-39`, `DOC-V1D-40`, `DOC-V1D-44`

### 4.5 Tier — Sense 1: Agent Tiers (0, 1, 2, 3)
- **Aliases:** `Reasoning Hierarchy`, `Overseer / Lead / Clerk / Scribe`
- **Canonical Definition:** Task/reasoning hierarchy: **Tier 0** (external overseer e.g. Claude/Codex outside vault via MCP `contribute`), **Tier 1** (`Lead`: session orchestrator & judgment inside a vault), **Tier 2** (`Clerk`: bounded drafting, descriptions, proofreading), **Tier 3** (`Scribe`: narrow chunk extraction, atomic formatting). **Oracle** (independent judge) and **Doctor** (scoped repairer) use isolated contexts and configured models (currently GLM-5.3).

- **Authoritative Sources:** `DOC-POL-02`, `DOC-V2E-04`, `DOC-POL-08`

### 4.6 Tier — Sense 2: Registry Permission Tiers (`consult`, `contribute`, `curate`)
- **Aliases:** `MCP Tiers`, `Access Tiers`, `Tool Tiers`
- **Canonical Definition:** Write-authority boundary enforced by `Registry` and MCP server (`mcp_server.py`): **`consult`** (read + log use/applications), **`contribute`** (stage proposals, open/decide session candidates, write drafts inside permitted session phases; max tier for agents), **`curate`** (accept staged items into library `Sources/`/`Concepts/`/`topics`, accept vault pipelines, approve `process_approved` batches — **Owner/person-only** when `promotion.mode='person'`).

### 4.7 Tier — Sense 3: Trust / Qualification Tiers (`gold`, `silver`, `bronze`)
- **Aliases:** `Confidence Tier`, `W5 Relation Tier`, `Graph Trust Score`

### 4.10 Ingest (`intake.ingest`) vs Enrichment Batch (`process_approved`) vs Acceptance (`staging_decide` / `promote`)

- **Evolution / Superseded Usage:** Cause of recurring model & user confusion since V2 launched (`DOC-V1D-30`, `DOC-V1D-34`, `DOC-MAP-02`). V2 consolidated V1's fragmented `populate`/`papers`/`enrich`/`lens` into these two explicit airlock gates.
