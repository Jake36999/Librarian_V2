## Executive finding

The 2026-10-28 research sprint was useful for understanding how to build and delegate to development agents, but it did not explicitly investigate a product long-horizon harness. This report is that dedicated harness research sprint and provides a design/evaluation direction. The local `audited-engagement-harness.md` is a design proposal, but some of its claims are attributed to an unidentified “Long horizon harness paper” and cannot currently be traced to a specific source in the research collection. Keep those claims as design hypotheses until that citation is recovered.

The literature supports a conservative direction: persistent, typed task state; explicit requirement and evidence tracking; bounded execution rounds; deterministic checks where possible; independent review only where it adds demonstrated value; recoverable checkpoints; and visible, correctable user-facing status. It does **not** establish that a reflection prompt, a confidence score, a swarm, MCTS, fine-tuning, or a latent world model will improve Librarian’s long-horizon performance. Several supplied papers are surveys, position papers, small prototypes, or domain-specific studies. Their concepts are useful as test hypotheses, not as product guarantees.

Recommended next move: use these findings to specify and test the existing HARNESS work, not to add a new algorithmic subsystem. Implementation and release sequencing remain governed by the unified plan and its dependencies; this research report does not authorize or sequence those tasks. Before treating the harness source claims as settled, resolve the unidentified “Long horizon harness paper” citation and the version/metadata issues listed below.

## Questions and method

The sprint examined: (1) whether recent research explicitly covers a product-style long-horizon harness; (2) what mechanisms could transfer to Librarian’s planned harness; (3) what evidence limits or negative results matter; (4) which goals and measures should be added to the harness evaluation; and (5) what runtime helpers and user-level monitoring should exist.

The supplied collection contains 51 PDFs. The initial pass selected and extracted 20 files; the supplemental pass added 17; the final pass covered all remaining 14, including one exact duplicate of an earlier source. The complete manifest records file identity, SHA-256, page count and extraction path. All files were screened for relevance, with targeted local reading and extraction of useful passages; this is not a claim to have replicated every experiment or exhaustively peer-reviewed every paper. Findings were compared with the implementation plan, harness proposal, prior sprint reports, workflow review, and Resource-Library application notes. DeepInfra supplied bounded source analysis, which was treated as leads and checked against local text for adopted findings. No product code was changed.

## Comprehensive harness goals and measures

These are goals to include in HARNESS-06/07’s evaluation design. Define a baseline, sample size, and no-go thresholds before product comparisons. Paper-specific thresholds (for example 0.7 confidence) are not product targets. Report quality–cost trade-offs rather than optimizing one metric in isolation.

| Goal | Example measurements and challenge cases |
|---|---|
| **1. Semantic drift and requirement fidelity** | Requirement survival by immutable requirement ID across round count; unauthorized relaxation rate; scope narrowing, exception injection, temporal relaxation, and priority inversion detection; correct preservation after user corrections and external edits. Include long tasks with tempting shortcuts and explicit “must/never” clauses. |
| **2. Task capability and planning** | End-to-end success by task class; subgoal completion and dependency violations; recovery/replan success; useful work per round; unnecessary decomposition; root goals added without user direction. Include task changes and ambiguous requests. |
| **3. Evidence quality and verification** | Unsupported claim, false-completion, false-accept, and false-reject rates; quote presence vs semantic support vs coverage; artifact correctness against deterministic oracles; verifier precision/recall and calibration. Include misleading but on-topic evidence and partial evidence. |
| **4. Reliability and resumability** | Completion and correct-state rates under interruption, restart, timeout, partial tool result, provider outage, retry, external file edit, and conflicting writer; duplicate side effects; stale-state use; checkpoint recovery; unresolved billing/result reconciliation. Exercise idempotency and uncertain outcomes. |
| **5. Token, cost, and latency efficiency** | At matched quality, report (a) accepted task completions per total billed dollar and per total input/output/cache token across all roles, and (b) cost/token per accepted completion; define accepted completion before the run. Also measure cost and latency by phase/route, context size and retrieval precision, retries, truncation, reviewer cost, user rework, and lead time. Include caps and p50/p95. |
| **6. Tool capability and policy adherence** | Tool selection success; correct argument/schema/path; useful-call rate; avoidable calls; policy-denied calls; side effects outside scope; composed multi-call authorization failures; tool result interpretation errors. Include hostile instructions in retrieved content. |
| **7. Safety, security, and abstention** | Prompt-injection resistance; privilege-boundary violations; protected-write escapes; sensitive-data exposure in logs; unsafe action rate; appropriate refusal/clarification; false execution vs false refusal. Test untrusted docs, conflicting instructions, secrets, and cancellation mid-operation. |
| **8. User agency and correction** | User can create/change/clarify goals; pause, resume, cancel, reject, or override; correction uptake and time-to-correction; user understanding of state and action; unwanted interruptions and rework. Do not optimize by inferring or scoring user “quality.” |
| **9. User-level observability and explanations** | Users can find active goal, requirement state, evidence, action/result, route/role, cost, blocker, stale status, and next decision; explanation accuracy and correction rate; event completeness. Explanations must be evidence-linked, not chain-of-thought. |
| **10. Context and memory quality** | Relevant retrieval precision/recall; provenance and freshness; stale memory invalidation; conflict detection; approved preference retention; omitted critical context; distraction from irrelevant context. Compare compact cited retrieval against larger context. |
| **11. Robustness and generalization** | Quality and safety across domains, task types, model versions/routes, long inputs, malformed state, missing tools, partial outputs, and adversarial or contradictory context. Track worst-case slices as well as averages. |
| **12. Model-role and routing consistency** | Correct model/adapter/route/config selection; schema compatibility; route failover; reviewer independence; same-model/shared-context correlation; behavior under unavailable/changed models. Keep route identity in each trace. |
| **13. Scalability and operability** | Bounded round behavior, event/log growth, projection latency, watcher load, monitoring signal-to-noise, queue/retry behavior, cost ceilings, schema migration and replay reliability. Exercise the planned 50-round case and longer stress runs. |
| **14. Privacy, trust, and audit integrity** | Data minimization and redaction; retention and deletion; access control; exportability; source integrity/hash validation; tamper-evident event history; user visibility into collected telemetry. Exclude covert productivity and sentiment scoring. |
| **15. Human usefulness and work quality** | Accepted outcome quality, time to useful result, interruption and rework, recovery burden, and user-rated usefulness. Separate subjective reports from objective task outcomes; do not generalize from anecdotes. |

Every metric needs a defined numerator/denominator and failure semantics. Report confidence intervals and slice results where sample size permits. Preserve false-accept and false-refusal counts; a single aggregate score can hide the safety trade-off.

## Recommended helpers and monitoring

The harness should expose compact, durable evidence to its own controller and to the user. Prefer a single canonical event stream plus deterministic projections over multiple competing sources of truth.

### Runtime helpers

1. **Session event log and reducer.** Persist typed events such as `requirement`, `artifact`, `fact`, `question`, `contract`, `verifier_result`, `reduction`, and `external_edit`. Store source identity, stable IDs, timestamps, and state epoch. Treat stale epochs as invalidated until reconciled. Hash-chain or otherwise make the event history tamper-evident.
2. **Requirement/task ledger.** Keep user-approved root goals, constraints, dependencies, acceptance criteria, and current status separately from model prose. Each action and completion must link to requirement IDs. Let the user approve scope expansion.
3. **Bounded manager projection.** Give the planner a compact state summary, open questions, relevant requirement IDs, tool manifest, budget, and recent event references, not the raw full transcript. Keep goal creation user-controlled.
4. **Provenance-aware retrieval.** Return exact source path/version/page or text offsets, short excerpts, freshness, and trust zone. Support evidence inclusion/exclusion and bounded context; never treat retrieved instructions as authority over system policy.
5. **Policy-filtered tool broker.** Use typed schemas, least privilege, path and operation scopes, size limits, idempotency keys, staging areas, and per-call audit events. Separate read, proposal, and mutation capabilities. A tool registry can report allowed capabilities to the planner without granting authority.
6. **Tier A deterministic verifiers.** Schema/format checks, quote matching, arithmetic, artifact diffs, declared tests, path policies, and source hashes. Report exactly what predicate was checked and its limits. For citations, distinguish source identity, quote presence, semantic support, and coverage.
7. **Tier B independent auditor.** Optional read-only reviewer for ambiguous/high-impact cases. Provide source snippets and requirement IDs, not the generator’s verdict as truth. Measure its false accepts/rejects and correlation. Do not expose hidden chain-of-thought to the user or store it as the audit record; retain the auditor’s concise verdict, predicate, and evidence links. It should not be the sole authority for a consequential action.
8. **Checkpoint and reconciliation helper.** Persist before/after state, invocation IDs, idempotency, timeout state, and provider response status. On resume, reconcile uncertain calls before retrying; cancellation must stop future side effects.
9. **Drift monitor.** Compare planned and completed action/evidence events with immutable requirements and contracts. Emit a small, explainable warning with the violated or at-risk requirement. Treat it as a signal requiring a check, not as an authoritative semantic score. Calibrate against human-labeled drift fixtures.
10. **Resource and budget controller.** Track per-role/phase cost and token use, reserve against explicit caps, and reduce retrieval or escalate only under defined rules. If a provider does not return usage, mark it unknown rather than carrying forward stale numbers.

### Monitoring and user interface

Each invocation should expose a trace ID, model/route/role, adapter/config hash, prompt-template ID and hash, source IDs/hashes and bounded offsets, tokens by input/output/cache and role, estimated/known cost, latency, retries, truncation, failures, tool calls and results, verifier predicate/strength/outcome, state diff/epoch, user corrections, cancellation, and recovery. Do not log raw prompt or source content by default; redact sensitive fields before any opt-in diagnostic capture and apply explicit access/retention controls. Attribute usage to each API call and reset per-call usage state to prevent stale cost attribution. Keep model and harness telemetry separate from user-performance evaluation.

The user-facing **status ledger** should show: the active goal; each requirement as open, complete, blocked, stale, or disputed; linked evidence/artifacts; actions and tool effects; why the harness is blocked or escalating; model route/role and cost; and the available user action (clarify, edit, approve, reject, pause, resume, cancel). Make indicators contestable and allow the user to inspect or correct them. Do not expose hidden reasoning or use confidence/sentiment as an unquestionable score. Provide visible privacy, retention, export, and deletion controls appropriate to stored traces.

## Evaluation and implementation direction

Use a quality-matched, staged comparison rather than adding all mechanisms at once:

1. **Baseline:** current route and transcript behavior.
2. **Externalized state:** typed requirement/task ledger and bounded state projection.
3. **State + Tier A:** add deterministic checks and recovery events.
4. **State + Tier A + Tier B:** add independent review only for defined uncertain/high-impact cases.
5. **Drift fixture variant:** add the labeled drift taxonomy and test warning precision/recall.

Run across multiple task classes and supported routes, at short/medium/long horizons including the planned 50-round case. Predeclare outcomes, cost caps, acceptance criteria, and safety no-go conditions. A Tier B verifier belongs in the default path only if its measured reduction in consequential false completion justifies its cost and false-rejection burden. Reflection, routing changes, and larger context should also be ablated independently.

### Suggested HARNESS alignment

- **HARNESS-01/02:** specify state schema, requirement IDs, event lineage, user-controlled root scope, and the manager/executor/auditor transition contract.
- **HARNESS-03/04/05:** establish verifier predicates, tool permissions, resumption, cancellation, idempotency, external-edit invalidation, and failure recovery. Use deterministic checks first.
- **HARNESS-06/07:** build the benchmark and monitoring/status ledger from the 15-goal matrix above. Preserve representative negative cases and evidence provenance.
- Add no dependency on RL, MCTS, swarms, fine-tuning, confidence thresholds, or latent world models unless a local controlled evaluation demonstrates value.
- Keep DEPLOY-01–04 and ACCEPT/RELEASE preparation moving on their own dependency paths; the research sprint does not require them to wait.

### E2′ Stage A0 is a strong local warning, with a narrow transfer boundary

The local [E2′ Stage A0 report](../2026-10-29-e2-prime-a0/README.md) reports mean normalized lead-effort ratios of **1.46** for one-shot delegation and **2.51** for the managed package relative to direct work, across three small behaviour-preserving refactors of 57–154 lines. The report says quality was equal across the nine arms; arm C used 1.58–1.96 times the effort of arm B on each task. Two managed-arm tasks escalated before paid delegation; the third delegated but still cost more. Fixed handoff, controller, review, and landing effort exceeded the short tasks. Its registered decision rule said stop for this task class.

This is compelling internal evidence to measure orchestration overhead and to avoid automatic delegation of small, short tasks. It is **not** proof of a general law for user-facing co-work or long-horizon tasks: the pilot has n=3 task instances in a particular coding/refactor class, and the report explicitly says larger tasks were not tested. It also does not prove the Mobile Agentic AI paper's theory. Treat it as a local prior and design constraint: compare inline execution with delegated modes at matched quality; include contract writing, controller time, model calls, review, retries, and merge/recovery in total cost; and decide by task class and horizon. A delegation/ROI gate should have an inline option and must be evaluated on longer and user-facing tasks before claiming a product-wide break-even rule.

### Corrections and cautions in the supplied formula-level claims

- **ReflectiChain:** the supplied equations and interpretation (including “intentionally” reinterpreting constraints, a rationale signal-restoration filter, and a universal “never reflect” implementation rule) should not be accepted from the reading-list text alone. The reviewed paper versions have differing methods/metrics and proxy-measure limitations. Use externalized constraints and deterministic checks as the baseline; test any reflective intervention by model, domain, and task pressure. Heavy prompts degrading performance in some conditions is a caution, not a ban on all reflection.
- **HPR-GenRM:** the source does describe adaptive depth using a 100-token shallow prediction and reports reward-hacking and process-verification results in its offline reward-model setting. That does not establish a zero-token entropy probe, a hosted-runtime feature, or the pasted specific “Tier A + Tier B is necessary” conclusion for Librarian. Its statistical/version issues and offline training requirements remain material.
- **Mobile KDR:** the paper supports a non-monotonic context-exposure hypothesis in its mobile/UAV experiment. Its measured K levels and context bundles are task/model-specific; the proposed K=3 projection is not a universal optimum or “exact theoretical justification” for Librarian’s Manager projection.
- **BBQL:** correction to this report’s earlier note—the supplied PDF does report **79.68% fewer explored nodes and 74.82% less computation time** against classic branch-and-bound in its job-shop scheduling experiments (PDF pp.5–6). The pasted suggestion’s claim that the exact small Q-table should order Librarian requirements is an extrapolation; those scheduling gains are not token savings, and the algorithm is domain-specific. The reported comparison is not an evaluation of an LLM harness.
- **TMS / Embodied Tree of Thoughts / KDRAR:** capability gating, pruning failed branches, and compatibility matrices are candidate patterns. Verify exact algorithms and pre/postconditions in those specific sources before mapping them to current Librarian APIs. The TMS paper does not establish the pasted MEA attribution; a research paper’s data structure does not itself authorize new product behavior.
- **“Zero-token” soft sensors:** deterministic counters (repeated tool signature, repeated error, stale epoch, missing evidence ID) can be zero-model-token checks. Embedding similarity generally needs an embedding computation and is only a proxy for semantic drift; a citation-to-sentence ratio is not proof of grounding. Keep these as separately named, calibrated signals, not a single QIV truth score.
- **PQL / taint composition:** a local declarative call-sequence policy is a plausible deterministic guard, but “50 lines” and direct applicability are not established by the paper title. Define trust zones, allowed effects, and exception behavior from Librarian’s own policy and test adversarial traces. Do not let an academic pattern silently redefine HARNESS-05 semantics.
- **E2′ ratio:** R(C)=2.51 and R(B)=1.46 are means of per-task lead-effort ratios, not a direct average of wall-clock minutes or a forecast for every task. The report’s table gives 95% t intervals with n=3; preserve that small-sample context.
