# Enrichment cycle requirements and evidence baseline

**Status:** analysis baseline for the proposed comprehensive integration, amended 22 November 2026 under the approved [graph review](../2026-11-22-ingestion-enrichment-graph-review.md). This report records the existing system and remaining integration work; it introduces no executable process, schema, storage service or permission grant. Source references are to the current `D:\Librarian_V2` checkout. Test references identify existing regression coverage, not a test run performed for this report.

The continuation preserves the Librarian's existing Core, registry, source intake, approved batch, staging, promotion, workflow-run records, model adapters, and canvas service. The main missing capability is coordinated execution and review across those boundaries. The full cycle includes folder classification, source capture, reading and derived knowledge, separately governed acceptance, publication and findability, followed by specification-based review and bounded remediation. It cannot be reduced to a PDF conversion followed by a generated summary.

## Owner decisions governing this baseline

The Owner's direction on 21 November, with the ownership correction on 22 November, resolves these points:

| Subject | Governing decision | Consequence for the model |
|---|---|---|
| Agent roles | Tier 0 Overseer; tier 1 Lead; tier 2 Clerk; tier 3 Scribe | Use those names in actor lanes and responsibilities. Legacy identifiers such as `tier3_agents` and `_profile_endpoint(..., "clerk", ..., 3)` are implementation facts to reconcile, not a reason to reverse the roles again. |
| Tier 0 | An outside agent may work on the user's behalf, use Librarian as support for another project, and delegate parallel work to the DeepInfra agents | Handover, delegated execution, review and escalation replace repeated manual orchestration where authority permits. This direction does not itself turn every existing person-only API into an agent-capable API. |
| Doctor and Oracle | Both are currently assigned GLM-5.3; the adapter/role-assignment system permits replacement when another model suits a role better | Model identity is a revisable assignment, not a schema constant. Context isolation and separation from worker execution remain requirements. |
| Fault register | A ticket service with tiered flags based on existing definitions and who should address the fault | Keep the fault's evidence, originating step/extension and responsible role. Do not implement the earlier four-bit proposal as the ticket model or invent a second severity taxonomy. |
| Specification ownership | Specification storage belongs within the Librarian Core | This report and its modeling artifacts are analysis inputs, not a competing runtime specification store. Exact persistence and APIs are later implementation work. |
| Core and agent ownership | Core performs scripted actions; the agent completing a proposal owns its interpretation and proposed values | Store specifications and proposals through Core without attributing authorship to it. Clerk owns neutral descriptions, meaningful Data organization, metadata and source-package review; Clerk/Scribe own model conversion. Lead owns coordination and explanations. Core checks schemas, literal evidence locators, counters, recorded grants and persisted state. |
| Composition | Action → workflow → pipeline → sprint, with earlier kinds directly usable by later parents | Preserve the existing runner and registry. A pipeline cannot define an action or workflow. Process layer is separate from agent tier, registry permission and content trust. |

## Evidence meanings and system boundary

**Implemented** means the behavior is present in the inspected source. **Covered** means an existing test asserts a relevant invariant. Neither label establishes a fresh passing test, live configuration, model qualification, or production readiness. **Planned** means the behavior is required by the adopted direction or continuation plan but is not supplied by the inspected runtime. **Conflict/gap** identifies a difference a faithful to-be model must show rather than conceal.

The Core owns mutable library state and calls the registry through the same writer, index, document leases and broker. The MCP process holds no vault state and refuses calls without a running Core ([mcp_server.py:1](../../src/resource_librarian/mcp_server.py#L1)). External actors include the Owner, tier-0 harness, model host and Geo-Grapher. A graph assignment, a folder description and a conversion artifact are distinct from reading source content and accepting a Source note.

References below retain the existing **UC1** step/extension numbers in [the written use cases](../2026-11-20-workflow-map/USE-CASES.md#uc1-make-a-folder-of-papers-into-library-knowledge-as-is) and the **to-be** extension IDs in [the accepted ingestion specification](../2026-11-20-workflow-map/examples/ingestion/ingestion-tobe.spec.yaml). Those are separate numbering schemes; this baseline does not renumber them.

## Gaps that the comprehensive model must expose

1. **General orchestration is not complete.** The existing process runner already validates definitions, pins all reachable definitions, uses append-only run records, and pauses uncertain writes rather than repeating them ([workflows.py:15](../../src/resource_librarian/workflows.py#L15)). W1b extends this foundation with state declarations, manifests, mandates, permitted compositions, run envelopes and the coded flows; it does not introduce another runner.
2. **Delegation has a concrete unresolved authorization boundary.** Tier-0 support/delegation is now explicit Owner direction, but current batch start/cancel and several reserved decisions remain person-gated. A correct to-be model shows the run's authority and authorized start separately. It cannot label the current UI-only start as already delegated, or erase it to meet the two-turn target.
3. **Oracle, Doctor and ticket routing are partly specified.** Existing claim review, audited verifiers and closure audit support them. Attaching the Oracle to any run, enforcing one specification owner and narrowing, routing tickets, executing accepted bounded remedies, rechecking, and one terminal notification remain the integration work. The example remedy catalogue says proposed workflows do not run yet ([remedy-catalogue.yaml:1](../2026-11-20-workflow-map/examples/ingestion/remedy-catalogue.yaml#L1)).
4. **The paper example needs complete internal coverage.** Its source-processing abstraction must account for validation, lenses, Data, internal relations, metadata and Bottom Line review, plus kind-specific inapplicability. Folder metadata enrichment is a separate branch. Paper graph publication and Source acceptance are separate outputs.
5. **Historical findings must retain dates.** OP1/F2/OP8 have source fixes; the older use-case index still describes pre-fix behavior. Current source and the detailed delivery record take precedence over the coarse status table. Historical test counts and 96-paper outcomes do not establish today's live state.
6. **Partial and conditional success need honest outcomes.** A source accepted with partial coverage, a non-PDF source, or catalogue-only graph material may be valid library content. None satisfies an unqualified guarantee of full reading and full paper-graph conversion. The Oracle checks the specification actually handed over and reports each exception.
7. **The accepted canvas is an owner artifact.** Its deliberate geometry/edge sides must survive. Use the existing safe canvas service, generated-ID ownership and `profile=None` geometry preservation. A structurally valid replacement diagram is insufficient if actor roles, coverage or visual method diverge.
