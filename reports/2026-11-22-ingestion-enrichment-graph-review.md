The proposed parent main success scenario is:

1. Owner or tier 0 states the goal, permitted roots, exclusions, required outputs and granted budget; the target Lead owns the run.
2. Core inventories and fingerprints; the assigned agent proposes semantic folder decisions; the authorized actor decides and Core applies them.
3. Core enumerates and reconciles eligible work by accepted root. Capture preserves evidence and per-reference outcomes; the assigned agent owns descriptions.
4. The authorized actor approves the staged work. Core admits the explicitly authorized start and freezes the selection.
5. The enrichment child returns per-item stage results, actual coverage, publication results and proposed outputs. The parent retains its original mixed-item ledger.
6. Source and independently staged lens outputs go to their respective decision owners. Folder metadata retains its separate review chain.
7. Core applies affirmative authorized Source decisions through the existing guarded writer and checks required findability. Held, declined and interrupted results remain explicit.
8. The target Oracle checks the parent's specified obligations; Lead returns one truthful full/partial/paused/escalated result to its specification owner. The as-is view shows the actors actually observed, rather than adding this proposed review loop to its history.

This is an end-to-end parent use case, not an assertion that a single runtime workflow already implements it. Compose only upward through action → workflow → pipeline → sprint, using existing accepted components at their actual layer. Do not place a pipeline inside a workflow or add a second execution/store mechanism.

### Conversion branch amendments

These guards are mutually distinct; the existing generic failed branch is too broad.

| Observed or proposed condition | Correct continuation |
|---|---|
| Usable generated representation, valid mapping and appropriate agent review | Store it and continue reading with its actual coverage. |
| Cleanup returns an error/timeout/429/refusal, with usable original extraction | Keep the reason; use original extraction; the current parse stage records `partial`. Continue applicable later work with that limitation. |
| Generated cleanup loses its page anchors, but original page-mapped text is usable | Retain generated evidence unused; use the original text layer. Current parse may be `complete` if no other gap remains. Do not force every anchor fallback to `partial` or `failed`. |
| OCR/representation leaves required material missing, or no readable text exists | Preserve partial/queued coverage and unmet tasks. Available later operations may proceed; absent content receives no reading credit. |
| Uncaught stage/writer failure | Record failed stage/item and preserve prior work; continue other items where the existing isolation rules permit. |
| Critical integrity or authority-boundary finding | Notify the Owner/tier 0 immediately and follow the critical stop/escalation path. This is not an ordinary conversion retry. |

These distinctions follow [current parsing/OCR](../src/resource_librarian/batch.py#L235), [publication](../src/resource_librarian/batch.py#L569), [stage reuse/execution](../src/resource_librarian/batch.py#L803), and [graph projection/admission](../src/resource_librarian/paper_graph.py#L77). My earlier conversion branches need this correction.

The corrected enrichment main scenario keeps the existing nine stages in order: validate → parse → read → lenses → Data → relate → metadata → review → publish. Core performs scripts, literal prefills, checks and persistence; agents perform interpretation, fidelity review and semantic proposals. Each item returns its actual result before the next frozen item. Required derivations and publication are checked separately from reading-part counters. In the target, the independent Oracle judges the package and any repaired requirements; Lead hands it back with the Source/lens decision obligations still explicit.

## Recovery scope and graph maintenance

Use the existing ticket flags, refusals and remedy cataloguing rules. A normal waiting decision, rejected optional lens or valid not-applicable result is not automatically a Doctor fault. The Doctor may execute only an accepted remedy within its actual scope; new remedies remain proposals. Core stores/routes the ticket; Lead owns unmapped diagnosis; Oracle judges and rechecks. Current Doctor/Oracle model assignment remains revisable through the adapters.

The configured Geo runtime currently cannot discover the audited `tree_sitter` packages, corroborating the missing-parser capability issue. The current receipt does not expose those parse failures; the stronger proposed coverage gate requires additional evidence. The follow-up preserves this current-versus-proposed boundary. Installing dependencies, changing retention or cleaning old generations are separate proposed maintenance actions, with the appropriate authority and verified active-generation references. Neither a WAL file nor a high byte count authorizes cleanup. The [existing R1 scope note](2026-11-20-workflow-map/examples/ingestion/remedy-catalogue.yaml) already warns that a seemingly local remedy can currently rebuild every group.
